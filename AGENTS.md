# SafeBooks Agent Instructions

## Read first

Inspect only the files directly related to the request, including the relevant view, service, model, template, browser-side code, and tests.

SafeBooks is a Django financial-management application. Changes must be narrow, explainable, and safe for bookkeepers and their clients.

## Project context

- SafeBooks uses Django 6, Django templates, vanilla JavaScript and CSS.
- Page and API routes are in `safebooks/urls.py`; request boundaries are in `safebooks/views.py`.
- Business logic belongs in `safebooks/services/`, persistent models in `safebooks/models/`, and tests in `safebooks/tests/`.
- SQLite is the local default; PostgreSQL is supported through environment configuration.
- The main workflows cover authentication, bookkeeper approvals, clients, financial records, dashboards, reports, settings, and audit logs.

## Working boundaries

- Work on the active feature branch. Do not switch, merge, reset, or modify `main` unless the user explicitly requests it.
- Preserve unrelated user changes. Do not delete, rewrite, or reformat files that are outside the requested scope.
- Do not modify database models, migrations, routes, authentication, authorization, financial calculations, audit logging, or external integrations unless the request requires it.
- Ask for direction before making a change that changes stored data, a public API contract, user permissions, deployment configuration, or a financial-recording rule.

## Architecture rules

- Keep request handling and authorization at the view boundary in `safebooks/views.py`.
- Put business rules in the appropriate module under `safebooks/services/`.
- Keep persistent schema changes in `safebooks/models/` and use migrations for model changes.
- Reuse validators in `safebooks/validators/` rather than duplicating validation rules in templates or JavaScript.
- Keep page markup in `templates/`, page styles in `static/css/`, and browser behavior in `static/js/` or the page's established script location.
- Preserve existing JSON field names and response envelopes unless a coordinated backend and frontend change is requested.

## Data and authorization safety

- A bookkeeper must only access and change their own clients and financial records.
- Preserve client ownership, record relationships, and audit history.
- Do not silently transform existing client data during a user-interface or validation change.
- Treat financial totals, line items, periods, reports, and forecasts as high-impact data. Trace the full calculation and persistence flow before changing them.
- Client transaction report previews and printouts must default to the current bookkeeping year. Show another year or combine years only when the bookkeeper explicitly selects that year or `All Years`.
- Treat passwords, client account credentials, recovery codes, OAuth secrets, and `.env` values as sensitive. Never print, commit, hard-code, or expose them.
- Keep database backups and data exports containing account, client, or financial data out of Git. Removing tracking does not remove historical copies; preserve local files and never rewrite history without explicit approval.
- Password resets must require short-lived, single-use authorization held in the server-side session of the browser that verified the code and bound to that account's current password. An email address or shared verified flag alone must never authorize a reset. Keep reset authorization proofs out of public responses and browser storage.
- Client lists and financial/report APIs must use directory-safe client summaries, never saved credentials or private custom fields. Full-profile reads and edits must enforce ownership and the configured client-details password lock at the view boundary. A verified grant is scoped to one client, expires, and is cleared on directory return or authentication changes. Report previews and printouts must never include passwords or password-type custom fields.
- Password and Google sign-in must complete configured 2FA before creating an authenticated session. Bind sessions and pending challenges to the account's current credentials and durable session version; reject legacy sessions without a proof. Password resets, password/2FA changes, recovery-code regeneration, and account deactivation must revoke older sessions. Only the current browser that proved a settings change may have its session renewed. Never return session authentication proofs to browsers.
- Password login reserves shared atomic five-minute attempt budgets before account lookup/hashing: 10 per normalized identifier/IP pair, 30 per identifier, and 60 per IP, counting successful attempts too. Use opaque HMAC cache keys, never passwords or raw identifiers/IPs. Cache failure must return a safe 503, not bypass the guard; excess returns 429 with Retry-After. Owner-approved exception (2026-10-19): password login distinguishes an unknown email/username (`field=identifier`) from an incorrect password (`field=password`) for both account roles. This deliberately discloses account existence; keep the `invalid_credentials` error code and response envelope, perform dummy hashing for unknown accounts, and never disclose account role, status, profile, or authentication proofs on these failures. Password-reset and other authentication disclosures are not covered by this exception. Verify the host's REMOTE_ADDR client-IP behavior before deployment; never trust user-supplied forwarded-IP headers implicitly. Preserve drafts and do not automatically retry sign-in.
- Production must explicitly select `safebooks.settings_production`, use hosting environment secrets (never the local `.env`), shared PostgreSQL sessions, and one TLS Redis primary for temporary authentication state and atomic attempt counters. Never silently fall back to local-memory caching. Verify proxy header trust before enabling it; keep localhost configuration separate. See `DEPLOYMENT.md` for build, release, and readiness checks.
- Financial create/update/delete operations must acquire the owned client lock first and commit record, line-item, related status, and financial audit writes together. Edit/delete requests must carry the revision received when the entry was loaded; stale or missing revisions must never overwrite or delete newer data. Keep notification emails after commit, preserve drafts on failed requests, and never automatically retry a write whose outcome is unknown.
- Validate submitted text against model field limits and financial numbers as finite `Decimal` values before persistence; retain existing two-decimal rounding, accept numeric zero, and reject entry totals beyond storage limits. Never truncate or rewrite existing values to make validation pass. Account email/username uniqueness must match case-insensitive lookups at the database level; handle uniqueness races only after rollback and never expose database exception details.
- Resolve client status from owned, non-future financial records, not empty periods. Closed remains Closed; the existing calendar-month 12-month inactivity rule takes priority over two recorded periods becoming Active. Retain manual remarks when neither automatic threshold applies. Page/API reads must never persist calculated status; explicit client/financial writes persist it under the owned-client lock, without bulk rewrites.
- Do not show successful logout until the server confirms session removal (or reports already unauthenticated). Failed/unknown writes must not clear authentication labels or redirect as if successful. Settings preferences and their audit entries commit together. Theme preferences are browser-local and require storage acknowledgement; email backend acceptance is not inbox delivery. Local preview backends must not pretend to deliver client or approval emails, and delivery errors must not log private message or exception details.
- Reuse ordered line-item prefetches or bounded batch loads instead of querying per record. Scope activity/deadline aggregates to the owner. Enforce the synchronous budgets in `safebooks/services/workload_limits.py` before returning financial histories or fitting forecasts; never silently truncate history, totals, or forecasts. Oversized reads must show a clear error, retain usable narrowing controls, and disable stale printing. Client report year choices must use lightweight owned metadata; fetch only the chosen year unless `All Years` is explicitly selected. These budgets do not replace PostgreSQL query-plan, browser, or simultaneous-user load testing.
- Group workflow counts without a correlated latest-record subquery per joined detail; preserve entry-date/ID ordering with a bounded latest-record batch. Analytics database failures return safe JSON 503 without partial data or exception details; loading/failure must not claim records are missing. Forecast requests may reuse identical immutable inputs only within that request, with independent client metadata; enforce the combined 8-distinct-fit/960-fit-observation budget before any fit. Unsupported, incomplete, or irregular histories do not consume fit budget. Restore drills must use disposable databases; before a real recovered system reopens, invalidate restored sessions/auth state and reconcile security changes lost after the backup. Never restore over a live database without explicit approval.

## Frontend change rules

- Client Details Lock is opt-in for new bookkeeper accounts, including password and Google signup (`client_details_password_required=False`). Preserve every existing account's saved On/Off choice; default-only migrations must not bulk-update preferences. Enabling or disabling the lock still requires the existing password-confirmed settings action, with ownership, grants, and audit handling unchanged.

- Workspace and admin toast notifications use the shared top-right container; child pages must not override it with bottom-positioned containers. Use stable semantic colors and brief non-flashing entrance feedback, honor reduced motion, and preserve notification text, timing, and write-confirmation behavior.
- Identical active notifications share one toast without restarting its timer; distinct notices retain their messages and timing inside a viewport-bounded, scrollable top-right container. Add/Edit coverage validation identifies Sales, Expenses, or a record detail in plain language and shows a short inline correction beside Covers. Keep the existing quarter-ending Record Date rule, preserve amounts and selected coverage while correcting the date, and never shift dates or retag saved records automatically.
- Analytics year selectors offer individual years only, not All Time. Derive choices from distinct owned financial-record period years in the relevant client scope plus the current bookkeeping year, select the current year initially, and never add empty-period years or hard-code calendar years. Monthly Trend and descriptive totals use only the selected year; legacy API requests without a year keep the rolling six-month chart window. SARIMA training includes earlier owned history through the selected year, never later-year observations; no-year requests retain full-history training. Bound the entire training history before fitting, show its available period range, and keep forecasts accessible when the selected year has no activity. Keep existing category/frequency grouping, consecutive-period requirements, model settings, and workload budgets; never retag, fill, or rewrite stored records to force eligibility. Readiness counts describe distinct periods, not transaction rows. Sales and expenses in Monthly Trend must share one peso scale derived from both series, never independent normalization. Keep month labels in one row, with columns matching the returned series even if an older stylesheet is cached; chart-only changes must not alter forecast inputs or stored financial records.
- Keep 404 recovery pages standalone and generic, with HTTP 404 status and no client details, exception text, or reflected request paths. Use Django's standard `404.html` behavior with `DEBUG=False` and `BrowserNotFoundMiddleware` for development browser GET/HEAD 404s. Keep debug mode enabled locally, preserve other error diagnostics, and leave API/asset responses and existing JSON API errors unchanged.
- Keep the familiar single Forecast layout without separate Monthly/Quarterly selectors or lengthy repeated explanations. The report uses one row per scheduled month, not an additional Q4/quarter-total row. Put native quarterly predictions only in their scheduled end-month cell with a short Quarterly label and retain exact coverage in its description. If both native monthly and quarterly predictions are scheduled, show both labelled values without adding or overwriting either. Label each insight card's period. Each independently labelled graph lane must use one frequency, never connect monthly amounts to quarterly totals within a curve. Never treat a quarterly amount as a monthly prediction or subtract it from a single month's sales. Quarterly Net Value may compare three monthly actual/forecast sales observations with quarterly expenses only with complete matching coverage, identified in the value's description; never fit another model, fill gaps, or divide quarterly amounts across months. Net Value remains sales minus expenses for identical coverage, excluding separately displayed tax. For Net Value, use Preview Report's additive recorded-entry semantics across every required monthly/quarterly component; never infer overlap, deduplicate, omit a component, or use one frequency as a replacement for another. Require complete same-period actual/forecast coverage and withhold net for missing, unsupported, unreliable, or misaligned components. Expose the two-decimal sales and expense bases used in net, with tax separate. Keep native frequency readiness independent, so short monthly history cannot hide a valid quarterly prediction. Horizon remains calendar months, quarterly anchors are preserved, and annual forecasting remains unsupported.
- Forecast Report cells explicitly label monthly values. Display calculated Net Value's matching coverage and sales-minus-expenses bases inline, not only on hover, so monthly Sales cannot be mistaken for the basis of a quarterly Net Value.
- All Clients forecast method labels may contain several semicolon-separated components. Any monthly-derived component prevents a total being treated as a native quarterly prediction. Preserve combined values in the report as a non-additive `Quarter total` that `Includes monthly`, with exact coverage and accessible clarification; never plot these comparison totals as native quarterly points or hide the matching calculated Net Value.
- The Projection Graph preserves one native frequency per independently labelled lane. Prefer native Monthly values when available for that category, otherwise native Quarterly values; never plot derived quarterly Sales comparisons in place of Monthly Sales. Keep the common calendar timeline, plot quarterly values only on their scheduled end months, and label each lane and point with its frequency and coverage. Net Value may use its already calculated, complete same-period result, never another fit. Report cells still retain both frequencies when present. Do not bridge rejected/missing scheduled periods or fill unscheduled months. Unavailable lanes show a short reason instead of a fabricated peso scale.
- SARIMA keeps its existing monthly/quarterly grouping, 24/8 consecutive-period minimums, settings, and fit budgets. Reject negative/non-finite predictions per period, never replace them with zero or suppress valid later predictions from the same fit. Propagate specific rejection reasons through both forecast consumers; graphs and sparklines must not interpolate through rejected periods. Tax/BIR classification alone does not establish frequency, history readiness, convergence, or valid predictions.
- Listed BIR forms resolve forecast frequency from the exact form/version metadata in `safebooks/services/tax_form_frequency_service.py`, before editable descriptions. Changing TW/PQ/QR or adding monthly/quarterly/annual words to a listed form's description must not change its grouping. A listed form without fixed-frequency metadata retains the saved parent frequency; custom/unlisted tax entries retain their existing legacy inference and fallback. Keep version distinctions, original saved dates/anchors, amounts, parent frequency, and description text unchanged. Do not infer coverage from VAT registration, force irregular histories to qualify, add annual forecasting, or treat this metadata as proof of a payment's covered period.
- For a new user-facing feature, validate the placement, responsive layout, modal open/close behavior, keyboard access, and visual states before connecting or expanding backend behavior. Recheck the complete UI-to-backend flow after integration.
- Inspect the complete create, edit, save, cancel, reset, and error paths before changing a modal or form.
- Keep existing form submission handlers, show/hide password controls, disabled styling, keyboard behavior, and accessibility attributes unless the request explicitly includes them.
- When a form uses a hidden field for its API payload, preserve its name, submitted format, and validation behavior.
- Use progressive enhancement for external browser APIs: show a clear loading or retry state and do not replace valid saved data if the external service is unavailable.
- Keep selectors, IDs, and data attributes stable when other scripts rely on them.
- Financial-line worksheet amounts (MICT, COGS/COS, income payments 2307, and tax withheld) are separate supporting values, never extra movements in totals, reports, Net Value, or SARIMA inputs. Blank means unrecorded (null); explicit zero stays zero. Tax Due uses the existing line amount. Preserve supporting values through edit/copy and reject older edit payloads that would silently drop them. Use “Enter when applicable” in the worksheet disclosure.
- Financial Records entry-page Preview Report sits beside Add Entry and fetches fresh owned report data on each opening, using directory-safe API client metadata without requiring a full-profile read. It defaults to the current bookkeeping year independently of the entry-page period filter. The report keeps Sales, Expenses, and calculated Net Sales once per month, aligned with the first saved tax form's Type/Code, editable saved Description, Tax Due, and separate worksheet amounts. Additional saved forms follow underneath without repeating the period or monthly figures; months without tax retain their monthly row. Keep all worksheet headings visible, preserve blank versus zero in saved values and editing, and keep supporting values out of financial totals. Worksheet preview and print render zero monetary values as blank cells. Preview and landscape print share the same ordered rows and columns; never sum numeric form codes, descriptions, or remarks. Preserve the report's blue typography, headers, borders, and standard total-row theme; keep Sales/monthly summary rows unshaded in preview and print. The report's Net Sales label uses the existing sales-minus-expenses result and does not rename forecast fields.

- Add and Edit Entry use matching ready Sales and Expenses fields without description inputs or Common Details shortcuts. Only listed BIR form descriptions are editable; keep existing non-form descriptions in the unchanged line-item payload. Preserve saved line order, duplicate lines, worksheet values, blank versus zero, revisions, and failed-write drafts. Clearing a ready amount does not remove any separate historical line. The last detail may be cleared to a blank row without clearing ready amounts; an entirely empty entry still cannot save.
- Selecting a tax form in Add/Edit Entry must leave a new Description blank for manual entry, without inserting its long form title. Keep typed, saved, and copied descriptions when switching forms or reopening entries. Keep the existing required-description validation and internal descriptions for non-form amounts; never bulk-clear stored descriptions or use manual wording to override a listed form's forecast frequency.
- Edit Entry corrects the existing entry, never copies it. When Record Date changes its month or year, show the original and destination months and require an explicit UI acknowledgement before submitting the move. Reset that acknowledgement when the destination month changes, the original month is restored, or the editor is reopened. Same-month day corrections use the normal update flow. Keep the existing date-to-period API behavior, revision checks, coverage validation, audit writes, failed-write drafts, and Add/Copy Previous flows unchanged; never repair or move historical entries automatically.

- Entry Remarks uses the existing `notes` field for the whole entry. Each listed tax form also has its own nullable line `remarks`, preserved through create, edit, copy, and report reads. Offer Paid and Pending for payment as editable suggestions, never defaults or inferred payment states. A saved form remark overrides entry remarks on that form's preview/print row, including the first form aligned with monthly figures; never combine other forms' payment remarks onto it. Legacy null retains the existing entry-remarks display; explicit blank suppresses that fallback. Collect non-empty form remarks from the current input value even when an input event was missed; retain legacy null only for untouched empty fields. Confirm explicit form remarks against the successful save response before closing/resetting the draft, and never automatically retry an acknowledged write with mismatched remarks. Do not backfill or rewrite historical remarks. Reject older edit payloads that would silently drop saved line remarks; keep financial amounts and SARIMA inputs independent of remarks.

- Worksheet preview and print show unrecorded Sales or Expenses with the standard empty marker, not a fabricated zero. Net Sales stays empty when neither category is recorded; retain the existing sales-minus-expenses result when either is recorded. Explicitly saved zero remains zero in storage and calculations, but worksheet preview and print render all zero monetary values, including zero totals, as truly blank cells. Do not hide zero text in descriptions, remarks, or non-monetary columns. Preserve financial totals, stored records, and forecasting.

- Worksheet preview and print show a Quarter column beside Period, derived from the saved report month (Jan-Mar 1, Apr-Jun 2, Jul-Sep 3, Oct-Dec 4). Show it on monthly rows and each additional saved form/detail row without repeating monthly amounts. Quarter is a display value, never a financial total, frequency replacement, filing-date inference, or stored-data rewrite.

- Insert exactly one completely empty worksheet row between different represented year/quarter groups in preview and print, after all forms from the preceding group. Do not add gaps between months in the same quarter, fabricate missing quarters, insert a leading/trailing separator, or include spacer rows in transaction data or totals.

- Add/Edit Entry replace the visible Record Frequency dropdown with separate Covers choices for Sales and Expenses. Save explicit `FinancialRecordLine.coverage_frequency` for these amounts; null retains the parent record's legacy frequency and anchor without backfilling history. Never infer coverage from a missing month, a quarter-ending date, VAT registration, or another category's amount. New explicit calendar-quarter amounts use March/June/September/December; annual amounts use December and remain unsupported by SARIMA. Preserve legacy non-calendar anchors until explicitly edited. Keep the parent's frequency field as a compatibility fallback, never use it to override explicit line coverage. Copy Previous retains each amount's coverage and supporting metadata; reject older edits that would discard saved coverage, confirm explicit coverage against successful save responses, and preserve drafts on failure without automatic retries. Forecast training and workflow counts use explicit Sales/Expenses coverage with legacy fallback; tax-form frequency handling, monetary calculations, observation minimums, and fit budgets stay unchanged. Reports retain the recorded amounts in their saved report month, without splitting quarterly totals across months.

- Dashboard reminders use the shortest represented Sales/Expenses coverage in the latest entry when explicit coverage exists, preserving legacy fallback for untouched amounts. Load only distinct owned latest-entry coverage metadata in one batch. Notification summaries and amount labels must reflect separate coverage without changing recipients, delivery preferences, or post-commit sending; financial audit writes remain atomic and describe the entry without assigning all its lines one frequency.

- New Sales/Expenses coverage choices offer monthly and quarterly periods only. Keep an existing annual value available when editing its saved line, without offering it for new amounts or creating annual SARIMA support. Add/Edit show Remarks only on listed tax-form rows; keep the existing entry `notes` input hidden, with its ID, name, payload, and saved value preserved for legacy fallback and copying. Show an inherited legacy remark in its tax-form input without converting an untouched fallback into an explicit saved remark. A changed or cleared form input overrides that fallback, including when an input event is missed. Do not remove the legacy database frequency or notes fields, rewrite history, or change financial/forecast calculations for these UI simplifications.
- Offer new quarterly Covers choices only for March, June, September, or December. If an already selected quarter becomes invalid after a draft date change, retain it as a disabled selected option with the existing inline correction instead of silently clearing or replacing it. Keep legacy saved coverage and annual edit compatibility. Financial Records has no entry-level Coverage column or repeated Coverage paragraph. Show each recorded Sales/Expenses amount's exact covered period in its expanded transaction detail, using explicit line coverage with the legacy fallback. Keep Add/Edit Covers choices unchanged. Do not assign one tax schedule from this display or change saved frequencies, dates, amounts, or forecast inputs.

- Client Tax Registration is a manual `tax_registration` choice: VAT (`vat`), Non-VAT (`non_vat`), or Not set (empty string). Existing clients start Not set, without inferring classification from tax forms, amounts, missing records, or record coverage. Add Client and both client edit flows preserve this choice; an older update that omits it must retain the saved value. It is directory-safe metadata displayed in client lists and Financial Records, while edits retain the existing ownership and full-profile password-lock checks. Registration is independent of client activity status, financial fields, taxes, coverage, and SARIMA; never use it to recalculate amounts, change form choices, hide worksheet columns, or retag financial history.
